Set the base

I collect colour, spacing, and type in one place before touching components. No one-off values on individual buttons or fields.

Name by role

Each value gets a name that says what it does — primary text, error background, focus ring — not what it looks like today.

Build on top

Controls pull from that shared set. Default, hover, focus, and disabled stay consistent because they share the same source.

Document as I go

Every component ships with a short spec next to it — enough for design review, dev hand-off, and later library updates.

What I keep

One naming logic across the file and the specs.

States tested before a component is marked done.

What I avoid

Detached styles and duplicate frames for the same state.

Docs that drift away from what is in the library.

What that gives

Faster screen assembly without breaking consistency.

A library that stays current when the product evolves.

A controls sample centred on buttons — illustrative, not exhaustive, but sufficient to review states and in-context documentation.

Full library

Extend the set with remaining components and complete documentation for each — states, anatomy, and usage notes in one place.

WCAG rules

Accessibility guidelines in markdown — contrast, focus, labels, and keyboard behaviour defined once in the system, not re-checked on every screen.

Usage & behaviour

Key examples of components in context — how they combine on real layouts and how interaction patterns behave across the product.

Consistency is the deliverable

A library pays off when change happens in one place and the product stays coherent. Shared foundations, names that describe purpose, and specs beside every control — that is what keeps design, development, and hand-off aligned as the system grows.
